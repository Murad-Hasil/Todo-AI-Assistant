# Implementation Plan: Browser-Visible Reminder Notifications

**Branch**: `016-browser-notifications` | **Date**: 2026-04-08 | **Spec**: [spec.md](./spec.md)

## Summary

When a reminder fires through the existing Dapr Jobs → Kafka → Notification Service pipeline, the user currently sees nothing. This plan adds a `user_notifications` DB table, saves a record whenever `publish_reminder_event()` fires, exposes two new authenticated REST endpoints, and wires up a frontend `NotificationPoller` component that polls every 10 seconds and delivers both a native OS browser popup (Web Notifications API) and an in-app toast strip.

**Scale/Scope**: Single-user demo; notifications table expected < 1000 rows per user

## Phase 0: Research

### Decision 1: Notification Delivery Mechanism

**Decision**: Web Notifications API (browser-native) + in-app toast div
**Rationale**: Zero new npm packages. `new Notification(title, {body})` works in all modern browsers on localhost. Toast is a simple fixed-position div with Tailwind — no library needed. This shows best in demo video (OS-level popup is visually dramatic).
**Alternatives considered**:
- react-hot-toast / sonner: Would work but adds a dependency; not needed since we only need one simple pattern.
- WebSockets/SSE: More real-time but requires persistent connection and server-side changes to notification service. Polling at 10s is sufficient for demo (reminder fires, 10s poll, popup appears).
- Service Worker Push: Requires HTTPS + VAPID keys + service worker registration. Overkill for local demo.

### Decision 2: Where to Save the Notification Record

**Decision**: Inside `publish_reminder_event()` in `app/logic/events.py` — directly after the Dapr publish call, open a DB session and insert a `UserNotification` row.
**Rationale**: `publish_reminder_event()` is already called from both the keyword trigger (task create) and the Dapr Jobs callback. Saving here means both paths are covered without touching any route handler.
**Alternatives considered**:
- Save in notification service: Requires the notification service to write back to the main DB — tight coupling, violates XII.
- Save in a new Dapr binding: Unnecessary complexity.

### Decision 3: Polling vs SSE

**Decision**: Client-side polling every 10 seconds using `setInterval` inside a `useEffect`.
**Rationale**: Simple, no infrastructure changes, works with port-forward or Minikube setup. 10s delay is acceptable for a reminder demo (reminder fires → 10s → popup appears).
**Alternatives considered**:
- SSE: Requires keeping a long-lived HTTP connection through the port-forward tunnel — unreliable in WSL2.
- WebSockets: Same issue + more complex.

## Phase 1: Design & Contracts

### Data Model

See [data-model.md](./data-model.md)

**UserNotification table** (`user_notifications`):

| Column | Type | Constraints |
|--------|------|-------------|
| id | UUID | PK, default uuid4 |
| user_id | VARCHAR | NOT NULL, index |
| task_title | VARCHAR(500) | NOT NULL |
| message | TEXT | NOT NULL |
| is_read | BOOLEAN | NOT NULL, default false |
| created_at | TIMESTAMP WITH TIME ZONE | NOT NULL, default now() |

Index on `(user_id, is_read)` for efficient polling queries.

### API Contracts

#### GET `/api/{user_id}/notifications`

- **Auth**: Bearer JWT required; `user_id` in path must match JWT `sub`
- **Returns**: List of unread `UserNotification` records for the user
- **Response 200**:
  ```json
  [
    {
      "id": "uuid",
      "task_title": "remind me to buy milk",
      "message": "Your task \"remind me to buy milk\" is due now!",
      "created_at": "2026-04-08T12:00:00Z"
    }
  ]
  ```
- **Response 403**: user_id mismatch

#### POST `/api/{user_id}/notifications/read-all`

- **Auth**: Bearer JWT required; `user_id` in path must match JWT `sub`
- **Action**: Sets `is_read = true` for all unread notifications of the user
- **Response 200**: `{"marked_read": 3}`
- **Response 403**: user_id mismatch

### Frontend Component Design

**`NotificationPoller`** (Client Component):
```
mount → request Notification permission
      → setInterval(10s):
            GET /api/{user_id}/notifications
            if results > 0:
              POST /api/{user_id}/notifications/read-all
              for each notification:
                new Notification("TodoAI Reminder", { body: task_title })
                setToasts(prev => [...prev, notification])
      → render: fixed toast strip (top-right, z-50, dark glass style)
      → each toast: bell icon + message + dismiss button
unmount → clearInterval
```

**Toast styling**: matches existing dark glass aesthetic (`bg-[#0d0d1a]`, `border-white/10`, indigo accent) — no new CSS classes needed.
